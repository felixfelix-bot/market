Thanks for the readiness gate — the bounded polling and three-state rollback classification are well-designed. Adding a few points beyond what maxime-tt covered:

1. **RISK — `install-staging-relay.sh:629` — `observe()` uses `bash SECONDS` which is a global mutable variable.** If `wait_for_readiness` or any called function also reads or modifies `SECONDS` (even indirectly via a subshell that inherits it), the observe loop deadline could shift. `SECONDS` is also reset to 0 on shell startup, not on function entry. Consider capturing `SECONDS` at observe entry into a local variable and computing elapsed manually, or route through `readiness_now` for consistency.

2. **RISK — `install-staging-relay.sh:491` — `check_runtime_sample` calls `check_growth` which calls `allocated` and `free_bytes` — 4 subshell invocations per sample.** During the readiness loop, this runs every `SAMPLE_SECONDS` (5s). Each `du` / `df` invocation on a relay data directory with significant storage could take non-trivial time. If the `du` takes >1s, the effective polling interval stretches. Not a correctness bug, but the timeout budget may be consumed by measurement overhead. Consider caching the `allocated` result or using a faster stat-based approach.

3. **NIT — `install-staging-relay-readiness.test.sh:280` — `test_readiness_wiring` is grep-based, not behavioral.** maxime-tt noted this. Adding: the grep assertions check line ordering via `cut -d: -f1` which is fragile — any reformatting that changes line numbers breaks the test without a functional regression. Consider asserting on behavior (e.g., that `observe()` is called after `wait_for_readiness` returns) rather than source line positions.

4. **NIT — No `shellcheck` CI step.** The test file itself is not shellchecked. `set -euo pipefail` is used, but the `sudo` stub uses `case "$1:$2"` pattern matching that would fail if `sudo` were called with flags before the command (e.g., `sudo -u user systemctl`). Not a current bug, but a latent fragility if the installer ever adds flag-based sudo calls.

5. **NIT — `deploy-relay.yml` — The workflow test step runs `bash deploy-simple/relay/tests/install-staging-relay-readiness.test.sh` but does not set `RELAY_READINESS_SECONDS`.** The test file exports `RELAY_READINESS_SECONDS=10` internally, but if the workflow environment has this variable set to something else, the test could behave differently. Consider unsetting or overriding in the workflow step explicitly.
