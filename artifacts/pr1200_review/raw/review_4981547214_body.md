## Review — PR #1200: ci(relay): add bounded staging readiness gate

Reviewed commit `6b8aeb6e`. All 33 tests pass, `bash -n` clean, shellcheck clean (only SC2015 info-level). The core readiness/rollback state-machine design remains sound. These are **new** issues not already covered by maxime-tt, felixfelix-bot, or Franchovy.

---

### 1. RISK — Workflow doesn't distinguish exit code 75 from 70

The script carefully returns `READINESS_TIMEOUT_STATUS=75` (readiness timeout, process still running, operator review) vs `70` (structural failure, manual intervention). But the workflow step that calls the installer has no `id:`, no output capture, and no conditional handling:

```yaml
"$deploy_dir/install-staging-relay.sh" "$deploy_dir"
```

Any non-zero exit = step failed. The three-state rollback classification is invisible at the CI level — an operator can't differentiate "review needed, process is up" from "structurally failed, service may be down" without reading step logs. Consider adding `id:` + `continue-on-error: true` + a conditional step that surfaces the distinction, or at minimum documenting that 75 vs 70 must be read from logs.

### 2. NIT — `check_growth` error messages lack context prefix

The PR adds context labels to `check_runtime_sample`'s direct errors (e.g., `"${context}: MainPID changed"`, `"${context}: boot ID changed"`). But `check_growth`, called within `check_runtime_sample`, emits context-less messages:

```
Staging raw allocation exceeded the emergency growth gate
Staging search allocation exceeded the emergency growth gate
Staging filesystem free-space loss exceeded the emergency growth gate
Staging relay data filesystem fell below the minimum free-space gate
```

During debugging, you can't tell whether a growth failure came from the activation readiness check, the post-health recheck, the rollback readiness check, or the steady-state terminal sample. Consider threading the context label into `check_growth` error messages.

### 3. NIT — `validate_payload` is extracted but untested

The PR moves payload validation from top-level code into a callable `validate_payload()` function — a testability improvement. But no tests cover it: missing binary, symlinked artifact, and mismatched systemd unit are all untested paths. The `test_readiness_configuration_validation` test validates `validate_config` (indirectly, via a spawned bash process), but `validate_payload` has no equivalent. Given that testability is this PR's headline, the newly extractable function should have at least a basic test case.

### 4. NIT — `rollback()` performs `du`/`df` I/O during service downtime

`rollback()` reads `allocated "$RAW_DIR"`, `allocated "$SEARCH_DIR"`, and `free_bytes` (lines 333–335) after `systemctl stop` but before `systemctl restart`. On a relay with large data directories, `sudo du -sx -B1` can take seconds — all while the service is stopped and the outage clock is ticking. Consider reading these metrics before stopping the service, or accepting the trade-off with a comment noting it.
