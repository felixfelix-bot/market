Thanks @hkarani — one name driving NIP-05 + vanity URL + a signed page is the right shape, and the schema-first block model reads cleanly. New findings at 2ae85b6f; the ten earlier items still stand and are not repeated.

1. [RISK] src/lib/schemas/storefront.ts:28 — `heroBlock.image` reuses `safeLink`, which only requires `https:` on *any* host, so a signed page event can make every visitor's browser fetch an arbitrary third-party URL. Verified: `parseStorefrontPage` accepts `{"type":"hero","title":"Hi","image":"https://attacker.example/pixel.png?u=1"}` and `StorefrontRenderer.tsx:26` puts it straight into `<img src>` — so a seller (or anyone holding a 30024 they can get rendered) gets a per-visitor tracking pixel and every visitor's IP/timestamp on a page we serve as ours. ADR-019:146-147 says images resolve through the existing Blossom/NIP-96 host allowlist; there is no such allowlist in this diff (and `src/lib/blossom.ts` only lists servers, no predicate). Please add an `ImageUrl` refinement gated on the configured Blossom/NIP-96 hosts plus the known server list.

2. [RISK] src/queries/storefront.tsx:40 — `fetchStorefrontPage` never Schnorr-verifies the 30024 event at the parse boundary. It filters on `kind`, `pubkey`, and the `d` tag only, then hands `event.content` to `parseStorefrontPage`. The repo already states the rule for exactly this case: "NDK's sampling verification may skip forged events, so we verify explicitly" — `src/queries/liveChat.tsx:93-99` calls `verifyNostrEventSignature` before parsing, and `src/queries/AGENTS.md` requires validating "signature assumptions before treating an event as application state". Without it a forged event with the right pubkey/kind/`d` and a bad signature renders on a public `/{name}` page. Add the seam check in the `candidates` filter.

3. [NIT] src/routes/_dashboard-layout/dashboard/account/storefront.tsx:56-58 — the editor textarea is unconditionally overwritten whenever `publishedPage` changes, with no dirty guard. `useStorefrontPage`'s subscription (`src/queries/storefront.tsx:59-63`) invalidates on *any* incoming 30024 from this pubkey, so a draft being typed is silently replaced by the relay copy — e.g. publishing from a second device/tab while the first is mid-edit. Track a dirty flag and only seed `content` when untouched (or on explicit revert).

4. [NIT] src/components/storefront/StorefrontRenderer.tsx:74 — this renders a `<main>` inside the `<main>` at `src/routes/__root.tsx:102`, so a storefront document ends up with two main landmarks (a11y: exactly one per document). `ProfilePage` returns a `<div>` for the same reason. Drop to a plain `<div>` or a `<section>`.

5. [NIT] docs/adr/ADR-019-unified-storefront-identity-and-page-builder.md:163-166 promises two guards for R5 — a renderer unit test asserting a hostile page renders inert, and an e2e path purchase → publish → `/{name}` → NIP-05. This PR ships only `src/lib/schemas/storefront.test.ts` (parser-level), and no e2e scenario references storefront or 30024. So the render layer is unverified for the exact threats the ADR enumerates. A small `StorefrontRenderer` test over a hostile page object would close most of it.

Happy to sketch the image allowlist refinement or the signature check if useful.
